# План переработки frontend — frontV4

Статус: планирование. Реализация ещё не начата.

## Цель

Переработать frontend так, чтобы изменение API и замена дизайна затрагивали ограниченные части приложения. Сохранить текущие пользовательские сценарии и подготовить ветку к последующему слиянию с основной веткой либо отдельному выпуску.

## Границы работы

- Работать с frontend. Backend не изучать и не изменять.
- Backend оставить в репозитории: его удаление не требуется для независимой архитектуры frontend и создаст ненужные изменения при слиянии.
- Не изменять существующие пользовательские правки вне согласованной задачи.
- Не менять API-контракты и поведение продукта без отдельного решения.
- Не выполнять публикацию, деплой или слияние автоматически: это отдельные последующие действия.

## Основные решения

### Изоляция API

Компоненты не должны знать адреса endpoint, названия сетевых полей и формат серверных ошибок.

Разделить сетевой транспорт, реализации запросов и преобразование ответов во внутренние модели. Сетевые DTO и модели приложения могут различаться. При замене API меняются запросы и адаптеры, а формы и сценарии продолжают работать с прежними внутренними моделями.

HTTP-транспорт не импортирует пользовательские stores, React-компоненты и уведомления. Получение токена и обработку завершения сессии подключает слой инициализации приложения. Устранить текущую циклическую зависимость API и store пользователя.

Загрузку JSON, файлов и изображений строить на общей транспортной основе. Формат ошибок нормализовать на границе API.

### Изоляция дизайна

Визуальные компоненты получают данные и обработчики через props. Загрузку данных, проверки прав, валидацию и управление действиями вынести в модели сценариев и хуки.

Общие элементы интерфейса и дизайн-токены сосредоточить в shared/ui и shared/styles. Предметные формы и таблицы собирать из этих элементов. Новый дизайн должен позволять заменять представление без переписывания сетевых запросов и правил работы приложения.

Не создавать универсальные абстракции заранее: выделять общие компоненты на основании реальных повторений.

### Организация кода

Начальная целевая структура:

```text
src/
  app/                 запуск, маршруты, подключение зависимостей
  pages/               сборка экранов и сценарии конкретных страниц
  entities/            модели сущностей, запросы, сетевые адаптеры
  shared/
    api/               HTTP-транспорт и общие ошибки
    realtime/          общие средства Socket.IO
    ui/                общие визуальные компоненты
    lib/               общие функции
    styles/            токены, шрифты, глобальные стили
```

Сценарии сначала группировать рядом с соответствующей страницей, например pages/account/registration. Верхнеуровневая папка features не обязательна; выделять её только при понятной необходимости повторного использования сценария.

Направление зависимостей: app → pages → entities → shared. Shared не зависит от предметных сущностей и страниц; entities не импортируют pages. App собирает зависимости и связывает инфраструктуру с приложением.

### Состояние

- Локальные формы, открытые редакторы и выделение — React state.
- Фильтры и параметры, значимые для навигации, — URL.
- Сессия, глобальные уведомления и действительно глобальные модалки — небольшие отдельные stores.
- Серверные HTTP-данные — единый механизм загрузки и кеширования. TanStack Query является кандидатом; решение о добавлении принять перед реализацией этого этапа.
- Данные реального времени — отдельные типизированные модели с явным владельцем подключения.

Не дублировать одни и те же серверные данные в нескольких независимых хранилищах без определённого правила синхронизации.

### Сокеты

Передавать leagueId, тип игры и авторизацию явно. Транспорт не читает window.location и не показывает уведомления. Разделить создание подключения, протокол событий и использование данных экраном.

Типизировать входящие события и исходящие команды. Определить жизненный цикл подключения, переключение лиги, отключение и обработку ошибок, включая одновременное использование данных таблицы и состояния показа.

## Этапы

### 1. Зафиксировать исходное поведение

- Составить перечень действующих маршрутов и пользовательских сценариев по frontend.
- Зафиксировать используемые HTTP-запросы и socket-события по клиентскому коду.
- Проверить исходное состояние typecheck и build, отдельно отметить уже существующие ошибки.
- Определить используемые и потенциально устаревшие компоненты; удалять только после проверки использования.

### 2. Подготовить инфраструктуру

- Разделить HTTP-транспорт, управление сессией и уведомления.
- Ввести нормализованные ошибки и явные зависимости транспорта.
- Создать основу структуры и правила импортов.
- Выделить чистую проверку прав из пользовательского store.

Критерий: транспорт не зависит от UI и Zustand; циклическая зависимость API и сессии устранена.

### 3. Перенести один законченный раздел

- Начать с мероприятий, затем перенести площадки и лиги.
- Разделить сетевые DTO, внутренние модели и формы.
- Вынести запросы, преобразования и управление действиями из компонентов представления.
- На этом разделе проверить выбранный механизм серверного состояния.

Критерий: текущие карточки, таблицы, редактирование, фотографии и проверки прав продолжают работать; экран не содержит адресов endpoint.

### 4. Разделить личный кабинет

- Вынести профиль, свою команду, регистрацию команды, пользователей и рассылки в самостоятельные разделы.
- Разделить форму, управление сценарием, валидацию и обращения к данным.
- Оставить странице выбор раздела и композицию интерфейса.

### 5. Убрать повторения в таблицах и модалках

- Сопоставить возможности DataTable, EntityTable и TeamTable.
- Объединить повторяющиеся механизмы сортировки, фильтрации и редактирования.
- Сохранить отдельные предметные редакторы и специальные игровые таблицы.
- Убрать зависимость глобального store модалок от типов UI-строк.
- Локальные окна разместить рядом с владельцем; проверить неработающие варианты реестра модалок.

### 6. Переработать результаты и показ

- Выделить типизированные socket-адаптеры и модели состояния.
- Отделить таблицы результатов от отправки игровых команд.
- Разделить логику показа, управления показом и визуальное отображение.
- Проверить переключение маршрутов, лиг и режимов, повторное подключение и очистку соединений.

### 7. Подготовить замену дизайна и завершить перенос

- Упорядочить общие UI-компоненты и дизайн-токены.
- Перенести оставшиеся экраны, включая журналы и QR-сценарии.
- Организовать маршруты и ленивую загрузку крупных экранов.
- Удалить подтверждённо неиспользуемый код и зависимости.
- Закрепить границы импортов автоматической проверкой.

## Проверка результата

Каждый этап должен быть небольшим и отдельно проверяемым. Не совмещать архитектурный перенос и полную смену дизайна в одном изменении.

- Выполнять typecheck и production build.
- Проверять затронутые пользовательские сценарии вручную.
- Добавлять целевые тесты на адаптеры данных, права, валидацию, завершение сессии и жизненный цикл realtime-подключений.
- Сохранять текущее поведение входа, выхода, регистрации команд, редактирования, результатов, показа и QR-сценариев.
- Изменение API проверять через адаптеры и клиентские фикстуры, не меняя backend.

## Работа с веткой и выпуск

Ветка frontV4 создана от текущей main. Делать небольшие тематические коммиты, сохранять возможность сравнения и переноса изменений. Перед слиянием учесть изменения, которые появятся в основной ветке.

Frontend собирается собственным Vite build. Возможность отдельного выпуска зависит от действующего способа размещения и совместимости с API; наличие ветки само по себе не делает её готовой к production.

Готовность к выпуску: завершён перенос согласованных сценариев, пройдены проверки, подтверждена совместимость с целевым API и отдельно согласован способ публикации.
