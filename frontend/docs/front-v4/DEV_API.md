# Переход на Python dev API

Дата сверки: 12 ноября 2026. Сервер: https://api.dev.kpiturnir.ru.
Пользовательский `frontend/spec.md` описывает целевые возможности; опубликованная OpenAPI содержит только часть из них.
Единый источник контракта: `frontend/openapi.json` (файл, предоставленный пользователем). Типы и допустимые маршруты генерируются непосредственно из него.
Генерация wire-типов и списка допустимых маршрутов: `npm --prefix frontend run generate:api-contract`.

## Подключение

В Vite запросы идут через `/api/`: proxy направляет их на HTTPS dev-сервер и удаляет префикс `/api`.
Это необходимо, поскольку проверенный ответ сервера на Origin `http://localhost:5173` не содержит `Access-Control-Allow-Origin`.
Production-сборка обращается напрямую к dev API; для домена размещения необходимо разрешение CORS на сервере.
Старый localhost:3000 больше не используется. Токен dev хранится отдельно, в `kpi_dev_auth_token`.

## Адаптированные разделы

- Авторизация: плоский `/auth/me`, `/auth/permissions` с authenticated/owner/grants, профиль через `/auth/me`.
- Мероприятия: чтение `/events` и `/events/{id}`. Площадки читаются из деталей мероприятия, лиги — из деталей площадки. CRUD структуры недоступен даже администратору.
- Роли: назначение через POST `/role-assignments`, отзыв через DELETE, просмотр `/users/{id}/roles`. Администратор имеет только глобальную область. Остальные роли поддерживают global/event/location/league.
- Права: используются действия из серверных grants и совпадение области по иерархии. Наличие owner-действий само по себе не разрешает изменение чужой команды. Поля команды ограничены `editable_fields` из ответа.
- Команды: фильтры в query-параметрах `/teams`, вложенные owner/league/location/event, lunches_count/accompanying_person, отдельные команды смены статуса и оплаты. Статуса PAID нет; используется is_paid.
- Кабинет: собственные команды, регистрация через иерархию структуры, редактирование профиля и команды, проверка оплаты.
- Пользователи: ответ items/total, загрузка следующих страниц через offset, редактирование без старых Telegram-полей, удаление и восстановление.
- QR: собственный подписанный QR через `/auth/me/qr`, поиск POST `/teams/by-qr`, отметка прибытия только при arrival_open и can_register. UUID больше не принимается.
- Технические работы: опрос `/maintenance`, режимы all/users; в users администратор может авторизоваться.

## Ещё не опубликовано на сервере

Маршрутов результатов игр, журналов, рассылок, генерации документов, изменения статуса лиги/презентации и протокола realtime в снимке нет.
Соответствующие экраны показывают недоступность или скрыты. Запросы вне опубликованного контракта блокируются до отправки.
Предыдущие модели этих разделов сохранены для последующего подключения, но это не подтверждённая реализация новой API.

## Проверка

`npm --prefix frontend run check`: границы импортов, строгие типы, клиентские тесты и production build.
Контрактные тесты проверяют вложенные ответы, отдельную оплату, допустимые поля заявки, grant/revoke ролей и запрет изменения структуры.
Публичные запросы `/openapi.json`, `/events` и неавторизованный `/auth/me` проверены на dev; записи на сервер не выполнялись.
Авторизация, письма, платёжный провайдер и остальные операции с записью требуют проверки с тестовым аккаунтом; клиентские тесты используют моки контрактных ответов.

## Завершение текущего этапа: главная и каталог

Главное мероприятие загружается через `/events/main`; 404 показывает отсутствие анонса, остальные ошибки — повтор загрузки. Кнопка регистрации видна при REGISTRATION_OPEN. Дата больше не задана текстом в главной странице.

Каталог содержит поиск и фильтр по статусу. Переходы идут по цепочке «мероприятие → площадка → лига», возврат доступен через верхнюю навигацию. Старые адреса мероприятия и площадки перенаправляют на соответствующие списки. Страница лиги показывает статус и переход к заявке.

Параметры eventId/locationId/leagueId сохраняются через авторизацию в returnTo, затем выбираются в форме только в пределах действительной иерархии API. Внешние адреса возврата запрещены. Закрытые лиги недоступны для выбора; при отсутствии открытых лиг на площадке выводится пояснение.

При публичной проверке dev главное мероприятие имело REGISTRATION_OPEN, но вложенные лиги — NOT_STARTED. Для фактического приёма заявок требуется открыть регистрацию в лигах; frontend эти данные на сервере не изменяет.

## Dashboard администратора

Вкладка `/lk/dashboard` (короткая ссылка `/dashboard`) доступна только роли admin в global с действием dashboard.view. Для остальных пользователей нет пункта навигации и не запускается запрос dashboard.
Данные берутся из полного ответа `/events/main`: главное мероприятие, все площадки и вложенные лиги, их статусы, команды, резерв и лимиты. Статистика агрегируется без сложения резерва с числом команд; лиги без лимита показаны отдельно. Данные автоматически обновляются каждые 30 секунд; доступно ручное обновление.

Публичная OpenAPI повторно проверена: маршрута изменения статуса лиги по-прежнему нет. Селектор и кнопка сохранения отключены с явным объяснением; старый неподтверждённый вызов setStatus заменён локальной ошибкой FEATURE_UNAVAILABLE. Для включения управления нужен подтверждённый контракт сервера. Права league.status и league.status_rollback учтены в модели, но запросы смены статуса не отправляются.

Блок возрастных лиг убран с главной страницы.

## Режим работы сайта

В dashboard показан режим из `/maintenance`: off — «Работает», users — «В работе», all — полные технические работы. Режим не включался: по просьбе пользователя подготовлено только поведение.

В режиме users основной интерфейс доступен только глобальной роли admin. Участники, неавторизованные и остальные роли видят заглушку. Точка после заголовка «Технические работы.» — доступная с клавиатуры ссылка на `/auth` с возвратом в dashboard. На этом входе нет регистрации и восстановления пароля. После входа пользователя без admin основной интерфейс остаётся закрыт.

До получения режима и проверки сессии показывается нейтральная загрузка, а не страницы сайта. Режим проверяется каждые 15 секунд, при возврате на вкладку и после ответа 503 MAINTENANCE; сессия при техработах не удаляется. Для администратора в users показана плашка «Сайт в работе». Режим all сохраняет полный запрет сайта согласно API-контракту, включая администраторов; наличие формы входа не обходит запрет серверной авторизации. Backend и его настройки не менялись.
