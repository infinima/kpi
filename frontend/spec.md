# Спецификация бэкенда: Турнир математических игр «Капица»

Версия: черновик 5 (обсуждение 12–14.10.2026: роли, статусы лиги, кварталы, ответы на открытые вопросы).
Статус: рабочий документ. Исходное ТЗ было самым первым вариантом, а не истиной в последней инстанции. Там, где написано «подтвердить», решение не принято.

## 1. Контекст и цели

Турнир математических игр для школьников 5–7 классов. Проходит два раза в год, ~250 команд на двух площадках. Платформа: сайт (фронтенд на TS, отдельный репозиторий), бэкенд (этот репозиторий, Python), Telegram-бот (Python, отдельный репозиторий).

Цели бэкенда:
- регистрация команд и личные кабинеты;
- проведение двух игр («Кварталы», «Фудзи») с подсчётом баллов и мест;
- приём и проверка фотографий бланков с ответами;
- онлайн-показ результатов;
- выгрузка дипломов, благодарностей и таблиц;
- журнал всех изменений.

Бэкенд переписывается с нуля (с TypeScript на Python). Старый репозиторий используется только как справочник по правилам и данным.

## 2. Глоссарий

- **Мероприятие (event)** — турнир (например, «Осенний турнир 2026»). Одно из них **главное**: оно отображается на главной странице.
- **Площадка (location)** — место проведения. Сейчас две.
- **Лига (league)** — возрастная группа на площадке. Проверка идёт по лигам, независимо от площадки.
- **Команда (team)** — участники одной команды, принадлежит лиге, владелец — пользователь.
- **Бланк (slip, «ответка»)** — бумажка с уникальным QR, привязана к команде (и косвенно к лиге, площадке, мероприятию). Команда печатает бланки заранее в личном кабинете и разрезает. **Один бланк = одна попытка = один ответ.** Номер задачи на бланке не указан.
- **Сабмишен (submission)** — одна фотография одного бланка.
- **Событие ответа (answer_event)** — результат проверки: команда, игра, номер задачи, «верно/неверно». Только добавляется, не изменяется.
- **Проверяющий (`checker_volunteer`)** — человек за компьютером, который видит фото и выставляет номер задачи и вердикт.
- **Фотограф** — волонтёр на площадке, который фотографирует бланки на телефон (роль `venue_volunteer`).

## 3. Роли и права

Роли хранятся в `role_assignments(user_id, role, scope_type, scope_id)`. Исключение — участник.

- **Участник** — владелец своей команды (`teams.owner_user_id`), в таблице ролей не хранится. Видит и редактирует только свою команду, печатает бланки, видит свои документы.
- **Оргкомитет (`organizer`)** — полное управление турниром в своей области: команды, лиги и статусы, штрафы, показ, проверка и замена фото, финальная таблица и дипломы, документы, логи. Рассылки — только у `admin`.
- **Волонтёр-проверяющий (`checker_volunteer`)** — берёт фото из очереди (по своим лигам), выставляет номер задачи и вердикт, может нажать «Не могу прочитать».
- **Волонтёр на площадке (`venue_volunteer`)** — регистрация команд на площадке (перевод в `ARRIVED`/`DOCUMENTS_SUBMITTED`; доступна только в соответствующем статусе лиги, см. 4.3), фотографирование бланков, выдача и приём кварталов (открытие и закрытие), смена статуса лиги, выставление штрафов.
- **Администратор (`admin`)** — технический суперпользователь (разработчик): всё, включая управление ролями, настройки и импорт. Это обычная роль в той же таблице, но выдаётся **только с областью `global`** (ограничение `CHECK` в БД). Отдельного флага `users.is_admin` нет. Роли выдаёт и снимает только глобальный `admin`.

Область (`scope_type`): `global | event | location | league`. Роль, выданная на уровне, действует на всё ниже (мероприятие → площадка → лига → команда).

- Матрица «роль → допустимые действия» хранится в коде, а не в БД.
- Загрузка презентации «Фудзи» (`league.presentation`) — у `organizer` и `admin`. Скачать презентацию можно либо с правом `show.view`/организатора/админа на эту лигу, либо передав `secret_code` лиги.
- Единая функция `can(user, action, resource)`; проверки в API и в сервисах одинаковые.
- Названия ролей единого вида: `organizer`, `checker_volunteer`, `venue_volunteer`, `admin`.

Матрица прав. ✓ — в пределах области роли; «своя» — только своя команда (участник — её владелец); «свои» — только записи самого пользователя; ⏱ — дополнительно зависит от статуса лиги (проверяет сервис, не `can()`).

## 4. Структура турнира

### 4.1 Мероприятие
- Мероприятие: название, дата, фото, набор шаблонов дипломов, статус и сезон.
  - Статус мероприятия: `ANNOUNCED` (анонсировано), `REGISTRATION_OPEN` (открыта регистрация), `REGISTRATION_CLOSED` (закрыта регистрация), `GAMES_IN_PROGRESS` (идут игры), `FINISHED` (завершено). Нужен только для главной страницы фронта; переход — любой в любой, меняется вручную в БД. Ни на что в API не влияет: регистрация, приход и игры определяются статусами лиг.
  - Сезон: `AUTUMN` или `SPRING` (осенний или весенний турнир) — для цветовой гаммы сайта.
  - Фото мероприятия: файл кладётся вручную в каталог хранилища (`Storage`), в `photo_key` — путь относительно каталога (например, `events/1.jpg`); API отдаёт его публично.
- Площадка: название, адрес, `photo_album_url` (ссылка на фотоальбом на сторонней платформе; модуля фотоальбомов в системе нет).
- Главное мероприятие задаётся настройкой `settings.main_event_id` (одно). Все настройки хранятся в таблице `settings(key, value)`; в первой версии значения меняются вручную в БД (DBeaver). Ключи техработ — см. раздел 13. API отдаёт главное мероприятие и его данные (площадки, лиги).
- Мероприятия и площадки через API **только читаются**: создания, правки, удаления и восстановления нет. Лиги тоже только читаются, кроме двух действий: смена статуса и загрузка презентации «Фудзи».
- У лиги есть `secret_code` (5 цифр, для открытия показа). Состояние показа лиги (экран, слайд, таймер) хранится отдельно, в `league_shows`.

### 4.2 Лига и статусы
Статус лиги можно переключить на любой другой (вперёд или назад). Переход через несколько статусов выполняется как цепочка одиночных шагов: условия и побочные эффекты каждого промежуточного статуса применяются по порядку, и если условие любого шага не выполнено, переход не происходит целиком. Установка текущего статуса — не ошибка: ничего не происходит. Менять статус может волонтёр на площадке и оргкомитет; откат назад — только оргкомитет (и админ).

```
NOT_STARTED
REGISTRATION_IN_PROGRESS
REGISTRATION_ENDED
TEAMS_FIXED
ARRIVAL_IN_PROGRESS
ARRIVAL_ENDED
KVARTALY_GAME
LUNCH
FUDZI_GAME
GAMES_ENDED
ENDED
```

Статусы `FUDZI_GAME_BREAK` и `AWARDING_IN_PROGRESS` из старой системы убраны. `REGISTRATION_ENDED` сохранён (между `REGISTRATION_IN_PROGRESS` и `TEAMS_FIXED`); побочных эффектов у входа в него нет.

Побочные эффекты и ограничения:
- вход в `FUDZI_GAME`: фиксируются места по Кварталам; переход запрещён, пока по лиге остались непроверенные фото «Кварталов»;
- вход в `GAMES_ENDED`: фиксируются места по Фудзи, считается итог, назначаются дипломы по умолчанию; переход запрещён, пока остались непроверенные фото «Фудзи»;
- «непроверенные» — фото в любом состоянии, кроме `graded` (`pending`, `in_review`, `unreadable`);
- откат назад сбрасывает зафиксированные результаты: `FUDZI_GAME → LUNCH` — места по Кварталам; `GAMES_ENDED → FUDZI_GAME` — места по Фудзи, итог и дипломы (включая ручные правки дипломов оргкомитетом). Остальные откаты побочных эффектов не имеют.

### 4.3 Статусы команды
`IN_RESERVE`, `ON_CHECKING`, `ACCEPTED`, `ARRIVED`, `DOCUMENTS_SUBMITTED`. Факт оплаты хранится отдельным булевым полем `is_paid`, а не статусом: оплата (например, с юрлица) может пройти позже прихода команды, и она не должна терять или блокировать статус.
В таблицы игр попадают только команды со статусом `DOCUMENTS_SUBMITTED`.
Перевод команды в `ARRIVED`/`DOCUMENTS_SUBMITTED` (регистрация на площадке, в том числе по QR команды) доступен только в статусе лиги `ARRIVAL_IN_PROGRESS`. Менять эти статусы могут `venue_volunteer` и выше (`organizer`, `admin`).
**QR руководителя** (как в старой системе — один на все команды руководителя). QR содержит ссылку на страницу сканера фронта с подписанным токеном (JWT, HS256, `sub` — id руководителя, без срока действия; все токены аннулируются сменой секрета). Руководитель получает свой токен в личном кабинете; письмо «QR для входа» содержит QR картинкой прямо в письме (встроенное изображение `cid:`). Волонтёр (любой с `teams.register` хотя бы в одной области) по токену получает все текущие команды руководителя — и из чужих лиг: название, школа, регион, сопровождающий, участники, ФИО руководителя, статус команды и лиги, признак «приход открыт» (лига в `ARRIVAL_IN_PROGRESS`) и признак «может отметить» (приход открыт и у волонтёра есть право на эту лигу). Отметить приход можно только в своей лиге.
После закрытия регистрации команды должны вноситься в таблицу **одним действием** (массовый перевод в нужный статус по лиге).

## 5. Регистрация и личный кабинет

- Регистрация и вход: пароль, одноразовые коды на почту, сброс пароля, сессии с хэшем токена.
  - Регистрация в два шага, как в старой системе: `POST /auth/register/start` принимает все данные (email, пароль, фамилия, имя, отчество — необязательно, телефон), на почту уходит 4-значный код на 5 минут; `POST /auth/register/confirm {email, code}` создаёт пользователя и возвращает токен. После 5 неверных кодов — блокировка на 15 минут.
  - Пароль — от 6 символов; телефон — `^\+?[0-9][0-9\s\-()]{8,20}$`.
  - Пароли хэшируются argon2id с секретным «перцем» из окружения (`HMAC(pepper, пароль)` перед argon2). Хэши bcrypt из старой системы принимаются и при первом успешном входе пересчитываются в argon2. Потеря перца означает сброс паролей у всех, поэтому он хранится отдельно от резервных копий БД.
  - Токен сессии — 32 случайных байта, передаётся в заголовке `Authorization: Bearer <token>`, в БД — SHA-256. Срок продлевается при каждом запросе: 30 дней для пользователей, 3 дня для персонала.
  - Вход: не больше 5 неудачных попыток за 15 минут на пару «email + IP», дальше `429` (счётчики в памяти процесса). Ошибка неверного логина или пароля — `401 INVALID_CREDENTIALS` без уточнения.
  - Сброс пароля: ссылка с ключом на 5 минут; запросы на сброс ограничены так же, как вход (5 за 15 минут на «email + IP»); ответ на запрос сброса не раскрывает, есть ли такой email; после сброса закрываются все сессии пользователя.
  - Роли во всех ответах API (`me`, карточка пользователя, список и выдача ролей) содержат, кроме `scope_type`/`scope_id`, объекты `event`, `location`, `league` (`id` и название) для области роли и всех областей выше; уровни ниже области — `null`.
  - Ошибки API — в виде `{"error": {"code": "...", "message": "..."}}`.
  - Свой профиль (`profile.edit`): пользователь меняет фамилию, имя, отчество и телефон; email сам сменить не может (только `admin`). Смена пароля — с вводом текущего пароля, неверный текущий пароль ограничивается так же, как вход; после смены закрываются все остальные сессии пользователя, текущая остаётся.
  - Управление пользователями (`users.manage`, только `admin`): список с поиском по email и ФИО и постраничным выводом (`limit`/`offset`), отдельно удалённые; карточка с ролями и командами пользователя (включая удалённые, с названиями лиги, площадки и мероприятия); создание пользователя (те же поля, что при регистрации, без кода подтверждения); правка ФИО, телефона и email (email уникален без учёта регистра среди неудалённых); задание нового пароля (закрываются все сессии пользователя) и отправка ему ссылки сброса; мягкое удаление (`deleted_at`, все сессии закрываются; команды и роли остаются, но роли не действуют, пока пользователь удалён) и восстановление (нельзя, если email занят другим пользователем). Удалить самого себя `admin` не может.
- Регистрация команды: владелец указывает лигу и признак `is_reserve`. Запись возможна только в статусе лиги `REGISTRATION_IN_PROGRESS`. Основная волна — команды в `ON_CHECKING`, `ACCEPTED`, `ARRIVED`, `DOCUMENTS_SUBMITTED`; пока в ней есть места (меньше `max_teams_count`), в резерв записаться нельзя (`RESERVE_NOT_OPEN`), когда мест нет — нельзя в основную волну (`TEAMS_LIMIT_REACHED`). Новая команда получает `ON_CHECKING` или `IN_RESERVE`. Оргкомитет и админ могут создать команду за другого пользователя (поиск пользователей по ФИО и email — только id, ФИО, email) в любом статусе лиги и без проверки мест.
- Личный кабинет: данные команды (название, участники — **ровно 4 человека**, массив без нормализации ФИО; школа, регион, количество обедов, сопровождающий), документы, оплата, статус.
- Печать бланков: пользователь указывает количество, система выдаёт PDF с N бланками (по несколько на лист, разрезаемыми), на каждом уникальный QR (случайный длинный токен, не угадываемый). Лимит — 50 бланков на команду (значение в настройках, при необходимости меняется).
- Письма: одобрение заявки, оплата, перевод в резерв и из резерва, исключение, QR для входа и т.д. (порт из старой системы).
- Рассылки: отправляются фоновой функцией внутри основного процесса (отдельного воркера нет). Получатели хранятся в таблице `mailing_recipients` со статусом `pending/sent/failed`; после перезапуска админ нажимает «продолжить», и доотправляются только оставшиеся.
- Оплата: интеграция с платёжным сервисом (порт из старой системы), ручная проверка оплаты по кнопке, поле `is_paid`. Автоматической проверки платежей по таймеру нет.
- **Резерв перед турниром.** За пару дней до турнира оргкомитет переносит из резерва всех, кого возможно, и переводит лигу в `TEAMS_FIXED`. Команды, оставшиеся в `IN_RESERVE`, получают письмо, что в турнир они, скорее всего, не попадут (только в исключительных случаях).
- **Защита от повторных писем.** Письмо про резерв уходит автоматически при входе лиги в `TEAMS_FIXED`; во фронте перед сменой статуса показывается предупреждение. Защита действует для всех автоматических разовых писем, привязанных к смене статуса (заявка принята, оплата подтверждена, перенос в резерв и из резерва, исключение, «не попадёте», QR для входа). Коды подтверждения и ссылки сброса пароля не дедуплицируются: их повторная отправка по запросу пользователя — штатное поведение. Оргкомитет (право `teams.manage` на команду) может отправить письмо повторно вручную. Отправка каждого «разового» уведомления фиксируется в таблице `team_notifications(team_id, kind, sent_at, status, error, UNIQUE(team_id, kind))`: запись вставляется до отправки (`pending`), фоновая отправка выставляет `sent` или `failed` с текстом ошибки; повторная смена статусов лиги или команды письмо второй раз не отправляет. Ответ на смену статуса команды перечисляет письма, пропущенные из-за повтора, а карточка команды для оргкомитета — состояние всех писем, чтобы фронт показал предупреждение и кнопку «переотправить». Письмо отправляется фоновой функцией, как рассылки.
- **Когда уходят разовые письма:** перевод в `ACCEPTED` — «заявка принята» (из `IN_RESERVE` — «переведена из резерва»), со ссылкой на оплату; `is_paid` стал `true` — «оплата подтверждена»; перевод в `IN_RESERVE` — «переведена в резерв»; удаление команды — «снята с турнира»; вход лиги в `TEAMS_FIXED` — командам в `IN_RESERVE` «скорее всего, не попадёте», командам в `ACCEPTED` — «QR для входа»; перевод команды в `ACCEPTED`, пока лига в `TEAMS_FIXED`, — тоже «QR для входа».

## 6. Игры

Во всех формулах N — число команд в таблице лиги (со статусом `DOCUMENTS_SUBMITTED`).
Штраф (`penalty`) у команды по каждой игре один: целое неотрицательное число, которое выставляется значением (не накапливается); он вычитается из итога. Неверные попытки — не штраф, они учитываются в баллах задач.

### 6.1 «Кварталы»
16 задач, 4 квартала по 4 задачи. Бланк = попытка.

- Задача **решена**, если есть хотя бы одно событие `correct`.
- Число **неверных попыток** по задаче = число событий `incorrect` (все, независимо от порядка проверки и от того, решена ли задача: бланки проверяются не в том порядке, в каком их сдала команда).
- Балл за решённую задачу = `5 + N − (число команд, решивших эту задачу) − (число неверных попыток этой команды)`.
- Бонус после каждого квартала (колонка «Бонус» после задач 4, 8, 12, 16): даётся, если решены все 4 задачи квартала. Стоимость = `5 + N − (число команд, получивших бонус за этот квартал)`.
- Нерешённая задача с неверными попытками даёт `−число попыток`; не сдававшаяся — 0.
- Итог игры = сумма баллов за задачи (включая отрицательные) + бонусы − штраф. Балл за задачу и итог могут быть отрицательными, ограничения снизу нет.
- **Открытие и закрытие кварталов.** У команды на руках может быть только один квартал: взять (открыть) новый можно, только если на руках нет ни одного. Сдать (закрыть) квартал можно в любой момент, даже если не выполнено ни одного задания из него. Сданный квартал обратно взять нельзя (каждый квартал берётся один раз). Порядок взятия кварталов любой. Кварталы выдаёт и принимает волонтёр на площадке: представитель команды подходит к нему с готовым кварталом или за новым.

Цвета в онлайн-показе:
- зелёный — решена с первой попытки;
- жёлтый — решена, но не с первой попытки;
- красный — не решена, есть неверные попытки (в ячейке `−число попыток`);
- пусто — не сдавалась.


### 6.2 «Фудзи»
16 задач, по одной попытке. Каждое событие задаёт статус: `correct`, `incorrect` (либо отсутствие события = не сдавалась).

- Балл за верно решённую задачу = `5 + (число команд, решивших эту задачу неверно)`.
- За неверно решённую или не сданную задачу = 0.
- Итог игры = сумма баллов − штраф.
- Поле `has_card` из старой системы (голосование за отмену вопроса) устарело и не переносится.

Цвета в онлайн-показе: зелёный — верно, красный — неверно, белый — не сдавалась.

### 6.3 Места в играх
- Сортировка по итогу игры (по убыванию).
- Штрафы в играх отдельные: штраф «Кварталов» и штраф «Фудзи» хранятся и считаются раздельно.
- Тай-брейк «Фудзи»: сначала по штрафу (у кого штраф больше, тот ниже), затем у кого больше баллов за последнюю задачу; при равенстве — за предпоследнюю, и так далее.
- Тай-брейк «Кварталов» сравнивает итоговые баллы за задачи (в т.ч. отрицательные за нерешённые с попытками) по порядку: штраф (у кого штраф больше, тот ниже), бонус 4-го квартала, баллы за задачи 16, 15, 14, 13, бонус 3-го квартала, задачи 12–9, бонус 2-го квартала, задачи 8–5, бонус 1-го квартала, задачи 4–1. Выше команда, у которой значение лучше на первом различающемся шаге.
- Если таблицы идентичны, всем делившим места присваивается **среднее место** (3 и 4 → по 3,5).
- Места хранятся как `DECIMAL(5,1)`.

### 6.4 Место в турнире
- Итог = сумма мест команды в обеих играх (меньше — лучше). Баллы игр в итоговом месте не участвуют.
- Тай-брейк: сравнение по последней игре (Фудзи), затем по предыдущей (Кварталы).
- Полное совпадение → среднее место.

### 6.5 Дипломы
По умолчанию, в порядке итоговой таблицы:
- 1-я команда — диплом 1 степени;
- 2–3-я — диплом 2 степени;
- 4–6-я — диплом 3 степени;
- остальные — диплом участника.

Порядок в итоговой таблице: по итоговому месту, а команды с одинаковым местом упорядочиваются по алфавиту названия. Если границу между степенями делят несколько команд, по умолчанию диплом получают те, кто выше в этом порядке; оргкомитет разбирается и может вручную изменить распределение в финальной таблице (так же, если из-за числа команд нужно другое количество призёров).

Для каждого мероприятия свой набор шаблонов дипломов.

## 7. Бланки и сканирование

### 7.1 Поток
1. Команда печатает бланки в кабинете.
2. Во время игры «ласточки» собирают бланки на площадке.
3. Фотографы снимают бланки на телефоны так, чтобы читался QR.
4. Фото попадает на сервер, система определяет команду (и лигу, площадку) по QR.
5. Проверяющие в общей очереди (по лигам) получают фото, указывают номер задачи и «верно/неверно».
6. Система пишет событие ответа и пересчитывает таблицу показа.

### 7.2 Приложение фотографа (PWA)
- Постоянный индикатор ✓/✗: читается ли QR в кадре сейчас. Распознавание локально (без запроса на сервер).
- Кнопка съёмки активна только при ✓. Снимок повторно проверяется на QR.
- Фото ставится в локальную очередь отправки (IndexedDB) и отправляется автоматически, с повторами при обрыве.
- У каждой записи очереди свой UUID (`Idempotency-Key`). Повтор той же записи возвращает успех, а не ошибку.
- Статус записи: ждёт → отправляется → ок / ошибка (бланк уже отправлен, неизвестный бланк, плохое изображение, нет сети).
- Локальное множество уже отснятых токенов — предупреждение о дубле на этом же устройстве.

### 7.3 Приём на сервере
- `POST /submissions` (multipart + `Idempotency-Key`). Ответы: `201` создан, `200` повтор своего запроса, `409` бланк уже отправлен (этот статус именно если такой токен уже был обработан, но с другии uuid), `404` неизвестный бланк, `422` плохое изображение.
- `UNIQUE(slip_token)`: на один бланк одно фото.
- Загрузка фото разрешена только в статусах лиги `KVARTALY_GAME` (игра «Кварталы») и `FUDZI_GAME` (игра «Фудзи»); игра определяется статусом. В остальных статусах — `409` с кодом `WRONG_LEAGUE_STATUS` (дубль бланка — `409` с кодом `SLIP_ALREADY_SUBMITTED`).
- Сжатие делается **на сервере синхронно, прямо в запросе** (отдельного воркера нет): повторное чтение QR по загруженному файлу, уменьшение до ~1600 px по длинной стороне, WebP. Оригинал не сохраняется, хранится только сжатая версия. Если сервер упал посреди запроса, телефон повторяет отправку с тем же `Idempotency-Key`.
- Одновременно сжимаются не более 2 фото (семафор), остальные запросы ждут; эндпоинты обычные `def` (пул потоков).

Состояния сабмишена: `pending → in_review → graded`; плюс `unreadable` (проверяющий нажал «Не могу прочитать», фото ждёт решения оргкомитета).

Если QR не читается или файл не удалось обработать, загрузка отклоняется ошибкой (`404`/`422`) и в очередь проверки не попадает; фотограф видит ошибку в своей очереди отправки.

### 7.4 Очередь проверки
- Проверяющий получает следующее фото запросом `UPDATE … WHERE id = (SELECT … FOR UPDATE SKIP LOCKED LIMIT 1)`.
- Аренда: 3 минуты; по истечении фото возвращается в очередь.
- Фильтр по лигам проверяющего; порядок — по времени загрузки. Две площадки обслуживаются одной общей очередью, распределённой по лигам.
- Проверяющий видит: фото, команду, лигу, игру. Вводит номер задачи (1–16) и вердикт.
- Исправление ошибки — компенсирующее событие, а не правка старого. Повторная проверка той же фотографии (например, перепроверка оргкомитетом или админом) — новое событие с тем же `submission_id`; в зачёт идёт последнее.
- «Фудзи»: у команды по каждой задаче может быть только одна фотография. Проверяющий не может указать номер задачи, по которому у команды уже есть другая фотография «Фудзи»; такой дубль — ошибка данных, а не вторая попытка. В «Кварталах» несколько фотографий по одной задаче — обычные попытки.
- Дублирующей проверки вторым проверяющим нет.
- Проверка ответов по задачам квартала не зависит от того, открыт или сдан квартал (фото попадают в очередь после сдачи). Система не проверяет, что номер задачи относится к кварталу, который команда реально брала: открытие и закрытие нужны только для правила «один квартал на руках».
- Если проверяющий не может прочитать ответ (почерк, размытое фото), он нажимает «Не могу прочитать»: сабмишен переходит в `unreadable` и уходит оргкомитету.
- Оргкомитет через админку может заменить фото конкретного сабмишена (загрузить другое). Замена записывается в журнал аудита, сабмишен снова становится `pending` (детали уточнить).

### 7.5 Данные
```
answer_slips(token PK, team_id, created_at)
submissions(id, slip_token UNIQUE, team_id, league_id, game, photo_key, uploaded_by, uploaded_at,
            state, assigned_to, lease_until, idempotency_key)   # game — по статусу лиги в момент загрузки
answer_events(id, team_id, game, task_no, verdict, submission_id, graded_by, graded_at)
team_quarters(team_id, quarter, opened_at, closed_at, opened_by, closed_by)   # «Кварталы», UNIQUE(team_id, quarter)
```
`answer_events` — источник истины. Таблицы показа считаются из событий. По каждой фотографии (`submission_id`) в зачёт идёт **только последнее событие**: оно определяет и номер задачи, и вердикт. Вердикты: `correct`, `incorrect`; «Не могу прочитать» — состояние фотографии (`unreadable`), а не событие ответа.

## 8. Онлайн-показ

- Таблица на каждую игру, обновляется по WebSocket/SSE при каждом новом событии (с небольшой задержкой на склейку).
- Колонки: команда, номера задач, баллы, бонусы (Кварталы), штраф, сумма, **место**.
- Сортировка по любому столбцу и автоматическая сортировка по месту.
- Выбор экрана показа: одна таблица или разделение пополам (2 колонки).
- Управление показом (заставка, таблица кварталы, слайды презентации Фудзи, таймер, таблица фудзи — порт из старой системы.
- Показ открывается только по ссылке `kpiturnir.ru/show/:league_id/:secret_code` (код — 5 цифр, поле лиги). Сокет показа и скачивание презентации принимают `secret_code` вместо авторизации; управляют показом только пользователи с правом `show.control`. Доступ к презентации: либо авторизованный организатор/админ этой лиги, либо верный `secret_code`.

## 9. Панель оргкомитета во время турнира

Длина очереди по лигам, количество фото в минуту по лигам, скорость каждого проверяющего по возрастным группам, нечитаемые бланки, фото в состоянии `unreadable` (ждут решения оргкомитета).

## 10. Фиксация результатов, документы

- В финальной таблице оргкомитет может вручную изменить степени дипломов до формирования документов.
- Результаты игры **фиксируются** при смене статуса лиги (см. 4.2) и после этого не меняются: новые события блокируются проверкой статуса. Исправление возможно только откатом статуса оргкомитетом с пересчётом.
- Выгрузки: дипломы и сертификаты/благодарности участников (PDF с названием команды и списком участников, благодарности доступны сразу начиная со статуса лиги ARRIVAL_ENDED в ЛК руководителей команд и организаторов. Сертификаты и дипломы доступны организаторам после формирования финальной таблицы, а руководителям в ЛК доступны только при статусе лиги ENDED), Excel с командами, скрипт награждения, презентация награждения (pptx), финальная таблица.
- Специальные номинации — порт из старой системы.

## 11. Апелляции

В первой версии отдельной функции апелляций нет. Если команда просит перепроверить результат, об этом сообщают в чат, и проверяющий или оргкомитет перепроверяет вручную: исправление делается корректирующим событием в `answer_events` (см. 7.4).

## 12. История изменений

- Все изменения ответов — через `answer_events` (кто, когда, что).
- Остальные сущности: журнал аудита (универсальная триггер-функция Postgres или запись в сервисах).
- Просмотр истории в интерфейсе: по команде, по пользователю.

## 13. Нефункциональные требования

**Нагрузка.** ~250 команд, ~10 тыс. фото за турнир, ~30 фотографов и ~10 проверяющих одновременно, пик 2–5 фото/с, десятки подключений к показу.

**Сервер.**
- Минимум (только прод): 2 ядра × 2,2 ГГц, 4 ГБ RAM, 40 ГБ SSD/NVMe.
- Рекомендуемые (прод + dev): 4 ядра × 2,2 ГГц, 8 ГБ RAM, 60 ГБ SSD/NVMe.
- Канал не менее 200 Мбит/с (лучше 1 Гбит/с): оригиналы фото 3–5 МБ.
- ОС Debian/Ubuntu LTS, статический IP, 80/443, снимки диска.
- Сервер на территории РФ (персональные данные детей).
- В дни турнира dev-окружение остановлено.

**Хранение.**
- БД: Postgres 16.
- Фото: интерфейс `Storage` (сначала локальный диск, позже S3). Оригиналы не сохраняются, хранится только WebP (~1600 px); WebP хранится бессрочно.
- Резервные копии: ночной `pg_dump` и копия каталога с фото **вне сервера**; периодическая проверка восстановления.

**Технические работы.** Два ключа в `settings`:
- `maintenance_mode`: `off` — работают все; `users` — техработы для пользователей; `all` — техработы для всех (пользователи и персонал);
- `maintenance_message` (текст) — описание техработ, одно для всех.

Группы: «пользователи» — участники и неавторизованные; «персонал» — все, у кого есть хотя бы одна запись в `role_assignments` (`organizer`, `checker_volunteer`, `venue_volunteer`, `admin`). Режим блокирует **и сайт, и API** для затронутых групп (`users` — только пользователи, `all` — все): запросы получают `503` с кодом `MAINTENANCE` и текстом `maintenance_message`, а фронт показывает этот текст вместо интерфейса. Всегда доступны: `/healthz`, `/readyz` и публичный `GET /maintenance` (отдаёт режим и текст, чтобы фронт мог показать заглушку до входа). Вход (`/auth/login`) проверяет группу после проверки пароля: если для группы идут техработы, возвращается `503 MAINTENANCE`. Страница показа и её сокет (по `secret_code`) блокируются вместе с функциями персонала — в режиме `all`. Группа определяется по сессии на каждый запрос (middleware), настройки читаются с коротким кэшем (несколько секунд), чтобы включение действовало почти сразу.

**Наблюдаемость (минимум).** Структурные JSON-логи с `request_id`; Sentry или GlitchTip; Uptime Kuma на другом сервере; эндпоинты `/healthz` и `/readyz`.

**Безопасность.** Хэш паролей argon2; токены сессий хранятся в виде хэшей; QR-токены случайные; ограничение частоты запросов на вход и загрузку; фото отдаются только авторизованным пользователям (проверка прав или короткоживущие ссылки).

**Тестирование.** Unit-тесты домена; golden-тесты на данных прошлых турниров (сравнение со старой системой); тесты гонок очереди; нагрузочная репетиция с имитацией 30 загрузчиков перед турниром.

## 14. Миграция данных

Скрипт `scripts/import_legacy.py` переносит данные старой БД (мероприятия, площадки, лиги, команды, пользователи, результаты). Данные прошлых турниров используются для golden-тестов.

К ближайшему турниру должны быть перенесены **все** функции старой системы (рассылки, специальные номинации, логи, проверка оплаты, письма, управление показом и т.д.), кроме явно помеченных «не переносим» в инвентаре (Telegram-вход, импорт команд по URL, модуль фотоальбомов, нормализация ФИО, автопроверка платежей). Старые данные команд `{coach, participants}` при импорте сводятся к 4 участникам. Инвентарь функций: см. `docs/legacy-inventory.md`. Статусы лиги `FUDZI_GAME_BREAK`, `AWARDING_IN_PROGRESS` при импорте заменяются на ближайшие по смыслу (правила — при написании скрипта).
